# SideQuest — CSCI 187

A student-built Santa Clara University event finder: **post an event → browse upcoming events → find full-fit availability → plan to attend → revisit or remove the plan.**

## Current M2 MVP

The React + TypeScript implementation on `master` includes:

- **EventCatalog posting:** title, host display name, description, location, date and time; fields validated before storage. IDs are generated by the catalog.
- **Discover and search:** posting and full-fit availability search use the same upcoming-event catalog after [PR #20](https://github.com/haiiroWednesday/SideQuest-CSCI187/pull/20).
- **My Schedule:** the user's plan IDs persist in this browser, remain sorted, warn about overlapping times and survive refresh. Removing a plan never deletes a public event.
- **Graceful states:** error messages, retry/loading, malformed-storage handling, and separate missing-event versus network-error states.

**Shared data requires setup:** If you configure a Supabase project and `app/.env.local` with a *publishable* key, the app uses the shared event catalog. Otherwise it explicitly warns that posted events live **in the current browser only**. The database adapter and SQL migration are committed, but real cross-browser operation must still be verified against a configured project. The fallback is appropriate for local tests, not a proof of public sharing.

The editorial **Campus Index** design is preserved on [Cynthia's separate UI feature branch](https://github.com/haiiroWednesday/SideQuest-CSCI187/pull/17) and is **not yet integrated** into the canonical application.

## Install and run

Requires [Node.js](https://nodejs.org/) 22.12+ (24 recommended) and Git.

```bash
git clone https://github.com/haiiroWednesday/SideQuest-CSCI187.git
cd SideQuest-CSCI187/app
npm ci
npm run dev
```

Open the local address reported by Vite, usually `http://localhost:5173/`. If you already cloned the repository, protect any uncommitted edits (`git status`), switch to `master`, and run `git pull --ff-only origin master` and then `npm ci` from `app/`.

**Optional shared database:** Daven's [app setup and Supabase guide](app/README.md) explains the reviewed SQL migration `supabase/migrations/20261103000000_create_events.sql`, a Supabase project, and `app/.env.example` to `app/.env.local`. Don't commit `.env.local`, service-role/secret API keys, or a teammate's Claude token. Database provisioning and the verification of read/insert permissions require authorized team access.

## Verify code and browser behavior

From `app/`:

```bash
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

[SideQuest React CI](.github/workflows/react-ci.yml) runs the React tests/build and Chromium checks in GitHub Actions on pushes/PRs. The separate root C++ course template retains its own CI but is not the React application.

**Human acceptance path:** In Browser A, post a future event to the configured shared catalog. In independent Browser B, refresh the catalog and confirm the event appears. Search a window containing the entire event; plan attendance; reload; remove the plan; verify Browser A still sees the posted event. Also test a valid 2,000-character description, bad inputs, a network failure and storage denial.

## Current project structure and architectural boundary

| Component | Responsibility |
| --- | --- |
| `app/src/App.tsx` and `app/src/view/` | View: forms, event cards, Schedule pages and user feedback |
| `app/src/controller/postEvent.ts`, `findEvents.ts`, `personalSchedule.ts` | Controller: mediate UI actions, use domain Model and translate errors |
| `app/src/model/eventCatalog.ts` and `events.ts` | Model: catalog rules, posting validity, event fields and full-fit search |
| `app/src/model/schedule.ts` | Model: device-local plan IDs, overlap rules, ordering and persistence |
| `app/src/model/supabaseEventTable.ts` | Model adapter: remote catalog operations |
| `supabase/migrations/` | Proposed SQL schema and anonymous-read/insert policies |
| `app/tests/` and `app/e2e/` | Unit/component and real-browser tests |

The historical M1-created-event list is retained locally for compatibility, distinctly from the M2 public catalog and personal Schedule. Do not automatically publish old browser records.
